Revenue recognition — schedule, journals and the startup guard

Reads invoices from the accounting system, works out what was actually earned in the period, and produces the recognition and bad-debt journal entries. Then it stops: posting back is a separate action a person has to take.

What is real here

  • The schedule layout, recognition bases and journal structure
  • Decimal arithmetic for money on both sides of the stack
  • The refuse-to-start-without-a-key behaviour
  • The explicit-approval-before-posting flow

What is invented

  • Every client name, contract reference and amount
  • The journal entry numbers and dates
  • The ageing that triggered the provision
  • The tenant name shown under Integrations

Three screens — use the menu or the tabs to move between them.

NamingThe tests are named for accounting, not for the framework. obligation engine, write-off recalculation, audit coverage, reconciliation. A failing test tells you which accounting rule broke.
StartupThe application refuses to boot without its encryption key. The refresh token is encrypted at rest with AES-256-GCM. If the key is absent the process exits rather than starting in a degraded state — a control in code, not a line in a README.

Two backendsThere are two, and that is a migration rather than a mess. The Node and Vite pair was replaced by the Python and Next pair. The process config names the live ones. Worth knowing before anyone clones it and runs the wrong scripts.

Reading this honestly

  • This is a reconstruction. The real application needs PostgreSQL and live accounting credentials.
  • The contracts were chosen to show the interesting bases — straight-line, milestone, metered, and one old enough to provision against.
  • The controls described are as implemented.
Why the repository is private. The code itself is private — it was built in a finance role and belongs to that context, so it is not published openly. Access can be granted on request for anyone assessing the work.
