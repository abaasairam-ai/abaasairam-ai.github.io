Revenue recognition — schedule and generated journals

Reads invoices from the accounting system, works out what has actually been earned in the period, and produces the revenue-recognition and bad-debt journal entries. Then it stops: posting back is a separate action a person has to take.

What is real here

  • The schedule layout, the recognition bases and the journal structure
  • Decimal arithmetic for money on both the Python and JavaScript sides
  • The refuse-to-start-without-a-key behaviour
  • The explicit-approval-before-posting flow

What is invented

  • Every client name — none of these companies exist
  • All contract references, amounts and percentages
  • The journal entry numbers and dates
  • The ageing that triggered the bad-debt provision

StartupThe application refuses to boot without its encryption key. The accounting-system refresh token is encrypted at rest with AES-256-GCM. If the key is absent the process exits rather than starting in a degraded state — a control in code, not a line in a README.

Reading this honestly

  • This is a reconstruction. The real application needs PostgreSQL and live accounting-system credentials to run.
  • The figures were chosen to show the interesting cases — straight-line, milestone, metered, and one contract old enough to provision against.
  • The controls described are as implemented. Those are the parts worth asking about.
