Reconciliation suite — three-input TDS receivable allocation

The largest of the ten. Four reconciliation modules; this is the three-input one, which takes the books ledger, a contacts export and the raw Form 26AS, works out which deductor each entry belongs to, and allocates entries to 26AS rows per TAN.

What is real here

  • The layout, navigation and every column of the allocation table
  • The confidence bands and how they are calculated
  • The source weights and the override behaviour
  • The allocation algorithm and its greedy fallback

What is invented

  • All client codes — ZULU, YANKEE and XRAY are placeholders
  • All TANs — the AAAA00001A pattern is a dummy format
  • Every amount, date, count and percentage
  • The deductor names, which are not real companies

Three screens — use the menu or the tabs to move between them.

AlgorithmAllocation is solved as an assignment problem. Within each TAN, books entries and 26AS rows are matched by minimising total cost across amount and date difference — not greedily, first-come-first-served. Above 500 rows in one TAN it falls back to a greedy pass, because the exact solve stops being worth the time.

PerformanceThroughput is measured, not assumed. A dedicated timing test and a stress-test script with banked results mean a slowdown shows up as a number in a test run rather than as a complaint from someone waiting.

Reading this honestly

  • This is a reconstruction. The real application needs Python, Node, a database and accounting-system credentials.
  • The numbers were chosen to show the interesting states — a clean match, a rounding difference, a date gap, a rejected outlier.
  • The tolerances, weights and the fallback threshold are as implemented. Those are the parts worth asking about.
Why the repository is private. The code itself is private — it was built in a finance role and belongs to that context, so it is not published openly. Access can be granted on request for anyone assessing the work.
