Billing API — import preview and request log

The backend behind subscription lifecycle, invoicing and client data. This screen shows the two things worth seeing: a bulk import that previews before it commits, and a request log where an unauthorised call is refused because nothing explicitly allowed it.

What is real here

  • The endpoint shapes, the /v1 versioning and the response codes
  • Money serialised as a string to preserve precision
  • Deny-by-default authorisation — the 403 is the intended behaviour
  • The dry-run then transactional-commit import flow

What is invented

  • Every client name, plan and amount
  • The row counts and rejection reasons
  • The client identifier in the DELETE call
  • All timestamps and record counts

ImportDry run first, then a transaction. A bulk import previews every row and what it would change. Only on confirmation does it commit — in one transaction, with an audit row written. A half-applied import is worse than no import, so the design makes it impossible.

PrecisionMoney crosses the wire as a string. "1,20,000.00", not 120000. JSON numbers are doubles, and a billing system that quietly loses the last paisa loses it everywhere at once. Serialising as a string costs nothing.

AuthorisationThe 403 above is the design, not a bug. The guard refuses unless a rule permits, rather than permitting unless a rule refuses. Adding an endpoint without adding a rule makes it inaccessible — which is the failure you want.

Reading this honestly

  • This is a reconstruction. The real service needs PostgreSQL with its migrations applied, and an identity provider for the role seam.
  • The import rows were chosen to show the validation outcomes that matter: clean, changed, duplicate and unresolvable.
  • The twelve database migrations behind this are named for what they did — that history is the evidence it grew under real use.
