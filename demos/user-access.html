Access register — grants and the leaver review

Tracks employees, software and the grants between them, so the access question has an answer before anyone asks it. Runs entirely on one machine against a file-based database.

What is real here

  • The employee-software-grant model and both screens
  • The leaver detection that surfaces open grants
  • Secure cookies gated on a dedicated variable
  • That the repository ships its own incident postmortem

What is invented

  • All employee initials — these are not people
  • Software names, roles and grant dates
  • Every count and review date

Two screens — use the menu or the tabs to move between them.

ConfigurationSecure cookies are gated on their own switch, not on NODE_ENV. A dedicated variable decides it, with a table in the README explaining when to use which. Tying cookie security to an environment name works until someone runs production with the wrong value.
Written up, not buriedThis repository contains its own incident report. A seed script once wiped rows from a live database here. The postmortem — root cause, paper trail, the policy change that followed — ships with the code.

Reading this honestly

  • This is a reconstruction. The real application needs its own environment secrets generated before first run.
  • The leavers with open grants are invented, but they are the exact case the register exists to catch.
  • Twelve test files back the real thing.
Why the repository is private. The code itself is private — it was built in a finance role and belongs to that context, so it is not published openly. Access can be granted on request for anyone assessing the work.
