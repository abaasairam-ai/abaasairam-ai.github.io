Access register — who has access to what

Tracks employees, software and the grants between them, so the access question has an answer before anyone asks it. Runs entirely on one machine against a file-based database.

What is real here

  • The register layout and the employee-software-grant model
  • The leaver detection that surfaces open grants
  • Secure cookies gated on a dedicated variable rather than NODE_ENV
  • That the repository ships its own incident postmortem

What is invented

  • All employee initials — these are not people
  • The software names, roles and grant dates
  • Every count in the stat strip
  • The review dates

ConfigurationSecure cookies are gated on their own switch, not on NODE_ENV. A dedicated variable decides it, with a table in the README explaining when to use which. Tying cookie security to the environment name is the kind of shortcut that works until someone runs production with the wrong value set.
Written up, not buriedThis repository contains its own incident report. A seed script once wiped rows from a live database here. The postmortem — root cause, paper trail, the policy change that followed — ships with the code rather than being quietly deleted.

Reading this honestly

  • This is a reconstruction. The real application is a Next.js app needing its own environment secrets generated before first run.
  • The three leavers with open grants are invented, but they are the exact case the register exists to catch.
  • Twelve test files back the real thing. The access model, not the UI, is the part worth asking about.
